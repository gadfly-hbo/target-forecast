# PRD：优惠券测算工具 P0（独立可运行的满减券情景测算与比较工具）

> 规格事实源：`.flow/proposal.md`（《优惠券测算工具 v2.0｜独立产品方案》固定稿）。
> 本 PRD 只细化与结构化，不改变提案决策；与提案的差异点在文末「PRD 差异清单」单独列出。
> 项目未配置 issue tracker，PRD 按 dev-flow 降级落盘于 `.flow/prd.md`。

## Problem Statement

业务人员在设计满减券活动时，面对"满多少减多少"没有可靠的算账工具：门槛以上的订单白白消耗补贴，门槛以下的订单可能凑单也可能流失，拉新的收益能否覆盖补贴全凭感觉。现有电子表格口径混乱（实付与券前金额混用、凑单失败一律当作保留成交、增量转化重复计数），无法回答：**是否发券、满多少减多少、需要多大转化提升才能回本、结论对哪些假设敏感**。

## Solution

一个本地优先、独立运行的优惠券情景测算与方案比较工具：导入基准数据（手工分桶 / CSV / XLSX）→ 配置券候选与行为参数 → 与无券基准同口径比较 → 查看统一收益账本、盈亏平衡与敏感性 → 人工确认并导出 → 活动后轻量复盘。所有指标出自同一组互斥结果分支（命中/核销、凑单/流失、转化响应、统一账本），允许"不发券"成为结论，参数证据状态全程可见。

技术上为纯 Python 确定性计算引擎 + 本地 Web 工作台（沿用本仓库 target_forecast 已验证的形态：标准库 http.server + JSON API + 无框架离线前端），不依赖任何外部平台、LLM 或网络服务。

## User Stories

**数据与基准**
1. 作为活动运营，我想手工录入基准订单的金额分桶（金额+权重+毛利），以便没有任何数据文件时也能完成一次测算。
2. 作为数据分析人员，我想导入 CSV / 标准 XLSX 的分桶或订单明细，以便用真实历史数据替换手工假设。
3. 作为数据分析人员，我想在导入时看到字段映射和口径确认（观察单位、窗口、金额口径=本次券前可用商品金额），以免用户口径和会话口径混用。
4. 作为数据分析人员，我想看到数据质量检查清单（空值、重复、A≤0、非法概率、权重不守恒、成本重复扣减等）并阻断或警示，以免带病数据直接出结果。
5. 作为活动运营，我想设置无券基准（N、C₀ 或降级为每单位口径），以便所有券方案都有同一对照。

**场景与参数**
6. 作为活动运营，我想配置候选券集合（分位数锚定自动生成 + 人工增补 + 禁用某候选），以便一次比较多个"满 T 减 F"组合。
7. 作为活动运营，我想在候选集中始终包含无券基准候选，以便"不发券"是一个显式可选结论。
8. 作为商品经营人员，我想分别配置原篮子毛利率、加购商品毛利率、券承担比例 ρ、可变费用与退货调整，以便补贴与成本口径如实入账。
9. 作为活动运营，我想为每个行为参数（触达 e、核销 r/r⁺、凑单 q 表或曲线参数、流失 d、新增转化 k/s_max/ΔC⁺、新增篮子 vⱼ）标注来源类型与说明，以便结果不被误当成已验证预测。
10. 作为活动运营，我想设置预算与业务约束（商家券预算、增量贡献底线、转化/GMV 目标、受控亏损开关），以便过滤不可行方案。
11. 作为业务负责人，我想在三种业务模式（毛利优先/转化优先/均衡）间切换目标，以便同一账本服务不同决策取向。
12. 作为活动运营，我想加载内置合成演示场景一键复现文档第七节结果，以便先学会工具再换自己的数据。

**比较与决策**
13. 作为活动运营，我想看到候选结果表（转化率、净转化变化、流失、毛新增订单、自然/加购核销量、商家补贴、总贡献、增量贡献、ROI、约束状态），以便横向比较。
14. 作为数据分析人员，我想展开任一候选的分支账本（每分支概率/期望订单/金额/毛利/补贴/费用/贡献），以便逐行复核公式。
15. 作为数据分析人员，我想看到 4.6 贡献拆解与总 ΔΠ 对平，以便确认解释与数字一致。
16. 作为业务负责人，我想看到回本条件（所需毛新增成交率 ΔC⁺_BE、对应转化率、是否超过可触达上限）与盈亏平衡提示，以便判断"需要多好才值得发"。
17. 作为业务负责人，我想跑单因素与保守/基准/积极联合情景的敏感性，看到各情景 ΔΠ、预算超限与否、排序变化与最敏感参数，以便不把单次排序当稳健结论。
18. 作为活动运营，我想看到四类结论（可行/需小范围验证/建议不发券或无可行/无法形成有效比较）而不是只有冠军，以便如实决策。
19. 作为活动运营，我想看到被过滤候选的过滤原因和邻近方案，以便被过滤的选项不凭空消失。
20. 作为业务负责人，我想填写决策卡（选择、证据状态、回本条件、最敏感假设、不利情景、确认理由），以便人工选择留痕且可复核。

**确认与导出**
21. 作为数据分析人员，我想导出 Markdown 决策摘要、CSV 逐候选/逐分支明细、JSON 完整运行记录（带场景版本、参数来源、引擎版本、运行 ID），以便沟通、复核与重跑。

**历史与复盘**
22. 作为数据分析人员，我想保存并找回历史运行（输入快照、配置、结果封存，改输入产生新运行不覆盖旧结果），以便结果可追溯可重跑。
23. 作为活动运营，我想导入活动实际汇总值，与预测对比并按偏差类别记录原因，以便完成一次不覆盖原版本的复盘。
24. 作为数据分析人员，我想在复盘后人工建立参数新版本（旧版本不变），以便经验沉淀不制造伪知识。

**工程与质量**
25. 作为数据分析人员，我想同一输入与引擎版本重跑得到完全相同的结果，以便导出与界面数值一致（M20）。
26. 作为开发者，我想让 M01–M20 验收场景全部成为自动化测试，以便引擎口径回归有机器判定。
27. 作为业务负责人，我想全程离线本地运行、不上传明细订单，以便数据不出本机。

## Implementation Decisions

**落位与结构（对提案 §10.1 的落位细化）**
- 在本仓库新建顶层 Python 包 `coupon_tool/`，与 `target_forecast/` 平级、互不依赖；提案的分层（domain/engine/data/storage/application/ui/adapters/tests）映射为包内平铺模块（沿用本仓库既有风格，不建八个子目录）。
- CLI 入口 `python -m coupon_tool`（子命令 serve / demo / console），独立于现有 main.py；不改动 target_forecast 任何文件。
- `tests/test_coupon_*.py` 独立成组，不动现有测试。

**核心接口（提案 §10.2，库优先）**
- `validate(spec) -> ValidationResult`（含数据质量检查清单）
- `simulate(spec, candidate) -> SimulationResult`（metrics + ledger + validation + limitations 四段，见提案 §11.3）
- `compare(spec) -> ComparisonResult`（候选表 + 约束过滤及原因 + 邻近方案 + 结论类型）
- `stress_test(spec, variants) -> SensitivityResult`
- `create_review(run_id, actuals, notes) -> ReviewRecord`
- 引擎版本常量 `ENGINE_VERSION` 写入每次运行记录。

**模型实现（提案 §四，逐字落实）**
- 四子模型按 4.2/4.3/4.4 分支表实现，分支概率合计=1 由 M04 测试锁定；Bᵢ 默认取 T 并标记"恰好凑到门槛"；qᵢ 支持用户参数表与演示曲线 `q_cap·exp(−λg)·min(1,(F/T)/d_ref)` 两种来源；转化响应含毛新增 ΔC⁺ 与净变化 ΔC 对账、C₀=0 限制提示。
- 统一账本按 4.5 记账（原篮子/加购/新增分开、商家券补/平台券补分开、K 只含新增固定费用）；4.6 拆解与 ΔΠ 对平作为引擎不变量测试。
- 金额内部整数分（int），概率与指数项 float，不逐分支过早舍入；阈值比较用整数分。

**约束与决策（提案 §五）**
- 约束：增量贡献底线（默认 ΔΠ≥0，受控亏损显式开启）、商家券预算对 B_m、转化/GMV 目标、单笔或分组贡献底线、净增量 ROI（B_m=0 → 不适用）、券合法性 0<F<T 阻断。
- 四类结论与邻近方案展示按 5.4；预算为过滤约束不截断成本（M18）。

**敏感性、盈亏平衡（提案 §六）**
- ΔC⁺_BE / C_BE / ΔC_BE 公式 + 上限检查 + 预算重算 + π̄_new≤0 提示。
- 敏感性参数覆盖：k（转化响应）、q_cap（凑单）、d（流失）、m_addon（加购毛利）、r（核销）、ρ（承担比例）；支持单因素与命名联合情景（保守/基准/积极）；范围由用户指定，无内置 ±20%。

**数据导入（提案 §3）**
- 手工分桶（UI 表格 / JSON）、CSV、标准 XLSX（openpyxl，模板生成到 templates/）；订单明细聚合成桶或逐单进入 Aᵢwᵢ；字段映射与口径确认；质量检查按 3.5 清单输出 error/warning 分级。
- 缺 N 时降级为每观察单位结果并明示（不输出活动总量）。

**存储（对提案 §10.3 的实现选择，见差异清单 D3）**
- 纯 JSON 文件快照：`coupon_data/` 下 profiles（参数档案带版本）、scenarios、runs（不可变运行记录：输入快照+配置+引擎版本+结果+校验）、reviews；run_id = 内容摘要 + 时间戳，变更输入产生新运行。

**导出（提案 §8.4）**
- Markdown 决策摘要（决策卡模板 8.3）、CSV（候选表 + 分支账本）、JSON（完整运行记录）到 `output/coupon/`。

**UI（提案 §8.1，单页四页签）**
- 一个工作台页面四个页签：数据与基准 / 场景与参数 / 比较与决策 / 历史与复盘；标准库 http.server + JSON API + 无框架静态前端（复用 target_forecast/server.py 模式）；候选结果表固定列按 8.2；决策卡按 8.3 模板；"先设置参数再给出结果"。
- 全局设计规范：项目无 DESIGN.md，UI 视觉默认基线为 `~/.zcode/design/DESIGN.md`（JuanerAI Xanthil 暖灰青工作台语言），实现时先读取该规范。

**演示场景**
- `demo` 子命令内置提案第七节合成场景（N=100k、五桶分布、全部行为参数），复现黄金表 10 行与压力表 4 情景；evidence_status=synthetic_assumptions，界面明示"合成演示参数，非行业真值"。

**边界与不做（提案 §1.4、§9.4、§12）**
- 不做自动发券/投放接口/实验分流/实时监控/多券叠加/个性化/自动训练/自动写回；adapters 只留接口占位不实现平台耦合；退货为情景估计 H；不伪造置信区间。

## Testing Decisions

- **测试哲学**：只测库接口（validate/simulate/compare/stress_test）的外部行为与账本不变量，不测内部函数；UI 只做 API 冒烟（先例：`tests/test_server.py`）。
- **黄金案例测试**：提案第七节基准表 9 行 + 无券行 + 压力表 6 值为黄金值，容差 ±1 分（转化率 ±0.0001）；先例：仓库 tests/test_core.py 的核心不变量风格。红队已独立复算确认公式-数值自洽（`.flow/red-team.md`）。
- **M01–M20 验收测试**：每条至少一个参数化场景测试，按提案 13.1 的"必须满足的行为"断言；明确不写"面额越大收益越小""门槛单峰"类非普遍性质测试。
- **不变量测试**：分支概率合计=1、账本订单数/N=转化率、4.6 拆解对平 ΔΠ、权重守恒、同输入重跑逐位一致。
- **导入与导出**：CSV/XLSX 往返、质量检查触发、导出 CSV 可再解析、JSON 运行记录可重放。
- **确定性**：不使用随机采样（P0 无需种子）。

## Out of Scope

- 提案 §1.4 与 §9.4 列出的全部"首期不做"（自动发券、实验分流、多券叠加、小时级监控、精美报告排版等）。
- P1/P2 扩展（精细加购篮子、类别成本、多券、分群）与 JuanerAI 平台接入（只留 ScenarioSpec/Result/Review 三接缝的 JSON 契约，不做适配器实现）。
- 不改动 target_forecast 既有模块与其测试。
- 不引入 SQLite（见差异清单 D3）、不引入前端框架/CDN/云端依赖。

## Further Notes

- 金额分/元换算只发生在显示层与导入层；CSV 导出同时提供分（内部口径）列。
- 「预算 10,000 元」示例（提案 7.2）作为约束测试场景之一（满159减10 超预算被过滤、满159减5 可行）。
- 引擎与 UI 间只经 JSON API 通信，保证 `python -m coupon_tool console`（无 UI 纯 CLI 测算）可用——门禁 B 的最短路径。

## PRD 差异清单（相对 .flow/proposal.md）

**新增（additive）**
- A1 落位：本仓库顶层包 `coupon_tool/`（提案只给 `coupon-tool/` 结构示意）；CLI `python -m coupon_tool`。
- A2 技术栈具体化：标准库 http.server + JSON API + 无框架前端（提案"本地 Web 界面 + Python"的建议落地为本仓库既有形态）；pandas/openpyxl 仅用于导入层。
- A3 UI 形态：单页工作台四页签（提案"一个工作区、四个主页面"的实现形态）。
- A4 金额精度细则：内部整数分、概率 float、黄金测试容差 ±1 分（对提案"整数分/不过早舍入"的具体化）。
- A5 UI 视觉基线引用全局设计规范 `~/.zcode/design/DESIGN.md`（项目无 DESIGN.md 时的默认，符合用户全局准则）。

**收窄/变更（需确认）**
- D3 存储：提案并列建议"SQLite 与文件快照"，PRD 选择**纯 JSON 文件快照、不引入 SQLite**——理由：单机单用户、快照可读可 diff、导出格式本就含 JSON、免 schema 迁移；提案对存储的真实要求（项目保存/快照/版本/运行 ID/重跑确定）JSON 全部满足。

**删除**：无。
